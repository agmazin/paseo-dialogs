# Загрузка диалогов 0.11.1

В 0.11.0 запрос dialogs.state ожидал последовательного восстановления всех unread-маркеров.
Для каждого маркера выполнялся timeline.refetch. Зависание одной истории блокировало
начальный state, после которого клиент только начинал agents/workspaces/terminals.
На основном host во время диагностики было 35 непустых unread из 86 сохранённых записей.
Это подтверждает наличие данных для этой ветви, но не измеряет задержку самого телефона.

В 0.11.1 начальный state возвращает состояние сразу после чтения файла и сверки папок.
Восстановление выполняется один раз в фоне, максимум двумя работниками: ожидание одного
запроса ограничено 5 секундами, общий бюджет составляет 10 секунд. После таймаута работник
останавливается, чтобы не накапливать физически неотменяемые SDK-запросы. Таймаут сохраняет
unread-токен. Ошибка провайдера удаляет только тот старый токен, с которым запрос начался.
Проверки текущего токена защищают mark-read и маркер нового хода; cleanup отменяет ожидание
и не позволяет поздним ответам дописывать маркеры или сохранять состояние.

Начальный state сообщает restoring. Если восстановление действительно идёт, клиент делает
один отдельный dialogs.state с waitForRestore=true. Ответ обновляет state в существующем
кеше, сохраняя полученные agents/workspaces/terminals. Это ограниченный long-poll, не опрос
по таймеру и не запрос на каждом render. При пустом unread нет дополнительного запроса.

Клиент использует native View/Text/ActivityIndicator/Pressable и цвета theme. Подключение,
загрузка, обновление и ошибка относятся только к списку диалогов. Ошибка предлагает
"Повторить"; повторное обновление и его ошибка сохраняют показанный список.
Ожидание запроса ограничено 20 секундами, встроенные повторные попытки query отключены.
Независимые workspaces/terminals начинаются одновременно с state; agents начинает читаться
после получения настроек раскрытого архива. Отмена не запускает последующие запросы.

Индикатор появляется только после загрузки самого расширения. Он не означает готовность
всех плагинов и не подменяет синхронизацию истории открытого чата. На Paseo 0.13.2 и 0.14.0
core удаляет установку расширения при отключении host; эти SDK handles не сохраняются
между установками. Повторное подключение выполняет новую подготовку штатным способом.

## Проверка

- Полный typecheck и регрессии проекта, включая имена, архив, порядок и перенос.
- Never-resolving history: исходный 0.11.0 state остаётся незавершённым после контрольных
  100 мс, новый state возвращается за 3.72 мс при той же неподвижной истории. Это локальный
  fixture с настоящим runtime.ts, без сетевого RTT, телефона или модельного хода.
- Реальный QueryObserver: медленная загрузка, первоначальная ошибка и Retry, кеш при ошибке
  refetch, offline/reconnect, 50 render без дополнительного initial RPC и единственный long-poll.
- Late read/new-turn guards, ограничение параллелизма и cleanup таймеров/подписок.
- Native-like отрисовка без DOM для светлой и тёмной темы.
- Отдельный daemon 0.14.0 на 127.0.0.1:16816, handshake mobile/0.13.2: компиляция, state RPC,
  plugin reload и получение status.plugin_catalog_changed. Ни телефон, ни основной daemon
  этой проверкой не изменялись. Временный daemon остановлен.

Доказательства находятся в ignored artifacts/ и .qa/: sidebar-readiness.json,
mobile-hot-reload.json, isolated-client-catalog.json, tests-mobile.log и typecheck-mobile.log.
Проверка на физическом Android не заявляется. Для воспроизведения before/after используется
tests/integration/sidebar-readiness.mts с PASEO_BASELINE_RUNTIME, для протокольной проверки -
tests/integration/mobile-hot-reload.mts с явно заданным временным PASEO_TEST_HOME.

## Доставка после технической приёмки

Сохранить текущий каталог /Users/agmazin/Library/Developer/paseo-releases/paseo-dialogs
для отката, скопировать туда файлы этой версии без node_modules/.qa/artifacts/.git,
проверить версию manifest/package и выполнить:

```sh
paseo --host 127.0.0.1:6767 plugin reload paseo-dialogs --json
paseo --host 127.0.0.1:6767 plugin logs paseo-dialogs --json
```

Подключённый Android получает status.plugin_catalog_changed, запрашивает актуальный
clientBundle и выполняет native contribution заново. APK, USB и перезапуск приложения
для этой доставки не нужны. При отключённом телефоне bundle придёт при следующем соединении.
Откат: вернуть сохранённый каталог и повторить тот же plugin reload.
